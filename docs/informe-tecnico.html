1. Qué es SITECORPAC

Es el sitio web institucional del Sindicato de Trabajadores de CORPAC (SITECORPAC), un sindicato peruano de trabajadores del sector aeroportuario. El sitio cumple dos roles a la vez:

  • Sitio público: noticias, ferias, sorteos, directorio de la junta directiva, legislación laboral, trámites (préstamos, beneficio por fallecimiento), información institucional.
  • Panel administrativo (/admin): donde el personal de oficina (no técnico) publica y edita ese contenido día a día, sin tocar código ni base de datos.

Es mantenido por un único desarrollador. No hay equipo de QA ni de operaciones: cualquier cambio que rompa producción lo nota primero una de las secretarias, no un sistema de monitoreo.

3. Arquitectura del código

El código sigue un patrón MVC explícito por módulo (noticias, ferias, sorteos, directorio, beneficios, etc.), encima de las convenciones de Next.js App Router. Cuatro capas, de arriba hacia abajo:

  1. Rutas API — src/app/api/**/route.ts. Parsean el request (JSON o FormData con archivos), verifican sesión/permiso con obtenerUsuarioActual() + tienePermiso(), y delegan al controlador. No tienen lógica de negocio.
  2. Controllers — src/controllers/*.ts. Validan reglas de negocio, orquestan subida/borrado de archivos, arman la respuesta y disparan revalidateTag() para invalidar caché tras crear/editar/eliminar.
  3. Models — src/models/*.ts. Única capa que llama a Prisma directamente (src/lib/prisma.ts). Cada método es una operación atómica (crear, actualizar, listar con sus include).
  4. Views / componentes — src/views, src/components, y las propias páginas en src/app/**/page.tsx. Client components ("use client") solo donde hace falta interactividad (modales admin, filtros, el selector de fotos, el visor de galería).

Las lecturas públicas (noticias, ferias, sorteos, directorio) usan unstable_cache de Next con revalidate: 60 y un tag por módulo, en vez de force-dynamic o caché manual en memoria de proceso — importante porque PM2 corre 2 instancias en cluster, así que un caché en memoria de un solo proceso quedaría desincronizado entre workers.

Estructura de carpetas relevante

src/
├─ app/
│  ├─ (público)/actividades/{noticias,ferias,sorteos}/...
│  ├─ admin/{noticias,ferias,sorteos,directorio,usuarios}/...
│  └─ api/
│     ├─ administrador/...        (rutas protegidas, requieren sesión + permiso)
│     └─ {noticias,ferias,sorteos,directorio}/...   (rutas públicas de lectura)
├─ controllers/     lógica de negocio por módulo
├─ models/           acceso a datos (Prisma) por módulo
├─ components/       piezas de UI reutilizables (galería de fotos, selector de imágenes, Toast...)
├─ hooks/            hooks compartidos (ej. useSelectorImagenes)
├─ lib/              utilidades: auth, permisos, validación de archivos, rate limiter...
├─ services/         wrappers fetch() usados desde componentes cliente
└─ views/            componentes de presentación "puros" reusados por página+cliente

Convención: modales y overlays van en un portal a document.body

Lightbox (visor de fotos) y Toast (aviso de éxito/error) se renderizan con createPortal(..., document.body) de React en vez de quedar anidados donde se llaman. Es a propósito: cualquier position: fixed anidado dentro de un ancestro con transform (como el .feria:hover / .card:hover de las tarjetas de ferias y sorteos, que aplican transform: translateY(...)) deja de posicionarse respecto al viewport y pasa a posicionarse respecto a ese ancestro — ver el gotcha correspondiente más abajo. Cualquier componente nuevo de overlay a pantalla completa (otro modal, otro visor) debería seguir el mismo patrón.

Esquema definido en prisma/schema.prisma, MySQL como motor. Las entidades de contenido principales:

Galería de fotos (agregada 2026-09-17)

Noticias, ferias y sorteos ahora soportan hasta 5 fotos, una marcada como principal. Cada entidad tiene su propia tabla de galería (noticia_imagen, evento_feria_imagen, sorteo_imagen), todas con la misma forma: 

id · <entidad>_id · url (VARCHAR) · orden (INT) · principal (BOOLEAN)

El campo legado de una sola imagen (noticia.imagen, evento_feria.imagen_portada, sorteo.imagen) se mantiene y se sincroniza automáticamente con la URL de la foto marcada como principal en cada creación/edición — así cualquier código que todavía lea ese campo directamente (tarjetas, carrusel del home, metadata OG) sigue funcionando sin cambios. La lógica de "qué foto queda como principal cuando se combinan fotos existentes + nuevas + una eliminación en el mismo guardado" vive en una única función pura, src/lib/resolverGaleria.ts, reutilizada por los tres controllers.

Migración de datos. El script scripts/backfill-imagenes-galeria.js convierte, una sola vez, la foto suelta que ya tenía cada registro en la primera fila (principal) de su galería nueva. Es idempotente: si un registro ya tiene filas en su galería, se salta. Correrlo después de cualquier prisma db push que recree estas tablas desde cero (por ejemplo, una base de datos de desarrollo nueva).

Límite de tamaño por foto y su validación (agregado 2026-09-18)

El límite de 10MB por imagen (MAX_IMAGEN_BYTES) vivía solo en src/lib/archivosNoticia.ts, que importa sharp y fs/promises — código de servidor que no se puede importar desde un componente "use client". Se extrajo a src/lib/constantesArchivos.ts, un módulo sin dependencias de Node, para que tanto los controllers (servidor) como useSelectorImagenes.ts (cliente) importen el mismo valor. El hook ahora rechaza en el momento cualquier foto que supere el límite (antes solo se enteraba el servidor al guardar, después de que la secretaria ya había llenado el resto del formulario), y el límite se muestra siempre en el texto de ayuda del selector.

Botón "Ver N fotos" fuera de la imagen (agregado 2026-09-18)

En las tarjetas de ferias y sorteos, GaleriaBoton dejó de ir superpuesto sobre la portada (position: absolute encima de la foto) y ahora se renderiza como un elemento normal del flujo, debajo de la imagen y alineado a la derecha (.galeriaBoton en ferias.module.css / sorteos.module.css). Los colores del botón (GaleriaFotos.module.css) pasaron de un pill oscuro semitransparente (pensado para ir sobre una foto) a un chip neutro de tarjeta, ya que ahora se ve sobre fondo blanco.

Servidor

Proceso

PM2, proceso sitecorpac, modo cluster con 2 instancias (ecosystem.config.js). Next corre con next start (build estándar, no standalone).

Red

nginx como reverse proxy hacia 127.0.0.1:3000, HTTPS vía Certbot/Let's Encrypt, HTTP/2 habilitado. /uploads/* y /images/uploads/* se sirven directo desde disco vía alias de nginx (no pasan por Next).

Imágenes subidas

El optimizador de imágenes de Next (/_next/image) está desactivado (images.unoptimized: true en next.config.ts) — ver el gotcha #2 más abajo para el porqué.

6. Procedimiento de despliegue

Sin CD automático: el despliegue a producción es manual, por SSH, siguiendo siempre este orden:

  1. Backup si el cambio toca el esquema: mysqldump con las credenciales del .env del VM, a un archivo con timestamp.
  2. sudo -u sitecorpac git -C /home/sitecorpac/SITECORPAC pull origin main
  3. sudo -u sitecorpac npm install --no-audit --no-fund
  4. npx prisma generate y, solo si el schema cambió, npx prisma db push (revisar la salida por advertencias de pérdida de datos antes de confirmar).
  5. Si hubo tablas nuevas de galería o similar: correr el script de backfill correspondiente.
  6. rm -rf .next && npm run build — limpiar .next primero evita errores de tipos por rutas/archivos eliminados en commits anteriores.
  7. sudo -u sitecorpac pm2 restart sitecorpac
  8. Verificar con curl -o /dev/null -w '%{http_code}' contra el sitio público y rutas API clave (200 en públicas, 401 en admin sin cookie).
Ojo: si git pull falla con "dubious ownership", correr git config --global --add safe.directory /home/sitecorpac/SITECORPAC (ya se configuró una vez, pero puede reaparecer).

7. Gotchas conocidos

sharp puede desaparecer en un install limpio

sharp (usado para comprimir/optimizar imágenes al subir) es una dependencia opcional específica de plataforma. Si no queda explícitamente listada en package.json (no basta con haberla instalado manualmente alguna vez), un npm install limpio en el VM puede perderla silenciosamente — rompe la optimización de next/image solo para fotos nuevas, mientras las ya optimizadas y cacheadas siguen viéndose bien, lo que lo hace parecer un bug intermitente. Está fijada en ^0.35.4; no dejar que se caiga del package.json.

Caché 404 de rutas de imagen nunca servidas por nginx

Cualquier imagen subida bajo una ruta que no tenga su propio alias de nginx (hoy: /uploads/ e /images/uploads/) pasa por Next. Si Next recibe una petición para un archivo que todavía no terminó de escribirse en disco, el App Router cae al boundary de "no encontrado" y cachea esa respuesta 404 para esa ruta exacta — no se autocorrige ni con el tiempo, solo con un pm2 restart. Si se agrega un nuevo tipo de subida bajo un prefijo de URL distinto a los dos ya cubiertos, hay que agregar el alias correspondiente en /etc/nginx/sites-available/sitecorpac antes de habilitar esa subida en producción.

El optimizador de next/image está apagado a propósito

Es la raíz del gotcha anterior: el optimizador interno hace un auto-fetch a su propia ruta interna, que puede quedar cacheada como "no encontrada". Se desactivó (unoptimized: true) y en su lugar las imágenes se comprimen una vez al subirlas (vía sharp, en src/lib/imagenes.ts) y nginx las sirve directo desde disco.

HTTP/2 importa para el rendimiento de primera carga

Con ~18 recursos estáticos por página, HTTP/1.1 los encola en lotes de 6 por el límite de conexiones concurrentes del navegador por host. HTTP/2 ya está habilitado (listen 443 ssl http2;) — si se migra de proveedor o se reconstruye la config de nginx desde cero, no perder esa línea.

Modal/visor que queda "encerrado" en su tarjeta en vez de cubrir la pantalla (2026-09-18)

Bug real detectado en producción: al abrir la galería de fotos de una feria y mover el cursor, el visor parpadeaba entre pantalla completa y un recuadro chico del tamaño de la tarjeta. Causa: Lightbox (position: fixed; inset: 0) se renderizaba anidado dentro de la tarjeta .feria, que tiene transform: translateY(-3px) en :hover. En CSS, un ancestro con transform se convierte en el containing block de cualquier descendiente position: fixed — así que cada vez que el cursor entraba/salía del hover de la tarjeta, el "fixed" del visor saltaba entre posicionarse respecto al viewport (sin hover) y respecto a la tarjeta (con hover). Arreglado moviendo Lightbox a un portal en document.body (ver la convención en la sección 3). Cualquier overlay a pantalla completa nuevo debe seguir ese mismo patrón, no solo depender de position: fixed dentro del árbol normal de componentes.

unstable_cache serializa Date a string en cache hit (2026-09-17/18)

TypeError: a.fecha.toISOString is not a function apareció de forma intermitente en los logs de producción. NoticiasController envuelve las lecturas con unstable_cache (ver sección 3): en un cache miss el valor devuelto viene recién de Prisma (con Date reales), pero en un cache hit Next deserializa el valor cacheado desde JSON, y Date se convierte en string. El código en src/app/page.tsx y src/app/noticias/page.tsx asumía que fecha siempre era Date y llamaba .toISOString() sin verificar. Cualquier dato que pase por unstable_cache y contenga campos Date tiene este mismo riesgo aguas abajo — tratar esos campos como Date | string, nunca solo Date.

CSP bloqueaba eval() en modo dev (2026-09-17)

La CSP de next.config.ts (sección 8) no incluía 'unsafe-eval' en script-src, correcta para producción pero rompía cosas solo en next dev: React/Next usan eval() en desarrollo para HMR y para reconstruir stack traces del debugger. Sin ese permiso, el modo dev queda en un estado roto (se observó, entre otros síntomas, el navbar sin responder a clics) sin que aparezca un error obvio más allá de un mensaje de consola sobre eval(). La CSP ahora agrega 'unsafe-eval' solo cuando process.env.NODE_ENV !== "production".

8. Seguridad

  • Login: máximo 5 intentos fallidos por IP en 15 minutos (contador en BD, no en memoria — necesario por el modo cluster). Contraseñas mínimo 8 caracteres, hasheadas con bcrypt.
  • JWT en cookie httpOnly, algoritmo explícito, duración de sesión 8h, con cierre automático por inactividad y aviso previo en el navegador.
  • Subida de archivos: whitelist estricta de tipos MIME (JPG/PNG/WEBP para imágenes), sanitización de nombre de archivo contra path traversal (src/lib/validacionArchivos.ts).
  • Cabeceras HTTP: CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy (ver next.config.ts).
  • Permisos por módulo: cada usuario admin tiene un JSON de permisos (user.permisos); tienePermiso() se revisa en cada ruta API protegida.

9. CI y pruebas

GitHub Actions (.github/workflows/ci.yml) corre en cada push/PR a main: tsc --noEmit, la suite de Vitest (reglas de seguridad más sensibles: validación de archivos, permisos, rate limiter, autoprotección de usuarios), y npm audit --audit-level=high en modo informativo (no bloquea el pipeline). No hay despliegue automático — el CI es solo verificación, el deploy sigue siendo manual (sección 6).

10. Correr el proyecto en local

git clone git@github.com:Jesusc169/SITECORPAC.git
cd SITECORPAC
npm install
# .env local con DATABASE_URL apuntando a un MySQL local (nunca a producción)
npx prisma generate
npx prisma db push
node scripts/backfill-imagenes-galeria.js   # si es una BD nueva
npm run dev

El servidor de desarrollo (next dev, Turbopack) puede mostrar errores que no aparecen en producción (build estándar) por diferencias de caché entre modo dev y build — si algo falla solo en npm run dev pero npm run build pasa limpio, confirmar contra el build antes de asumir una regresión real.
